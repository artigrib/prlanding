Guide · 30 Oct 2026

Before the parts arrive: LeRobot against a virtual arm

SO-101 parts usually take 21 to 28 days in the post. You can use that time: our so101-virtual program runs a virtual SO-101 in the MuJoCo physics simulation and exposes it as a serial port. The real, unmodified LeRobot then talks to it exactly as it would to a real servo board. You set servo IDs, calibrate, drive the follower with the leader, record a dataset and replay it.

Tested on 30 Oct 2026 with LeRobot 0.6.1 (PyPI), feetech-servo-sdk 1.0.0, Python 3.12 and Node.js 22 on Linux (x86_64). macOS should work the same way but is untested; for Windows see below. The virtual arm is for practice: factory values, load and heat are approximate, not measured on real servos.

01 — How it works

Software in the loop: real software, virtual hardware

The program runs in Node.js and does three things. It steps a physics model of the arm in real time (the same MuJoCo model as our browser simulation). It emulates six Feetech STS3215 servos on one half-duplex bus: they answer the same packets as real servos (PING, READ, WRITE, SYNC READ, SYNC WRITE, REG WRITE and ACTION) and have the same register table. And it exposes the bus as a virtual serial port (a pseudo-terminal), for example /tmp/so101-follower.

Neither LeRobot nor the Feetech SDK can tell: they open the port, set 1 Mbaud and send packets. Optionally a second, virtual leader arm runs on its own port. A script, the keyboard or a recorded trajectory moves it instead of your hand.

02 — Install

Node.js, Python 3.12 and LeRobot 0.6.1

You need Node.js 20 or newer and Python 3.12. The so101-virtual program lives in our website's repository and has no npm dependencies. A small helper written with the Python standard library (pty and termios) creates the virtual port.

git clone --depth 1 https://github.com/artigrib/prlanding.git
cd prlanding

python3.12 -m venv .venv-lerobot
source .venv-lerobot/bin/activate
pip install "lerobot[feetech,core-scripts]==0.6.1"

It is the same install as in the SO-101 assembly and first steps guides, so you can keep the environment for the real arm (core-scripts includes dataset; our test run on 30 Oct used the narrower [feetech,dataset], core-scripts adds packages for hardware and visualisation). We pin the LeRobot version we tested. A newer one will most likely work too, but parameter names may differ.

Our note: on Linux, pip downloads PyTorch with the CUDA libraries (over 4 GB). The virtual arm needs no GPU; to save space, install the CPU build first as described on pytorch.org.

03 — Start

The virtual arm in a first terminal

node tools/sil/so101-virtual.mjs --leader --auto-hand --mirror

It prints the ports of both arms: follower /tmp/so101-follower, leader /tmp/so101-leader. The servos already have IDs 1 to 6, as if the IDs had been set (you can practise the servo ID step separately, see the next section). Keep the window open and run LeRobot in a second terminal with the same Python environment.

Port. lerobot-find-port looks for real USB devices and will not find the virtual port. You do not need it: the ports are fixed and the program prints them. Use --follower-port and --leader-port for other paths.

The --auto-hand switch does the part of calibration you would otherwise do by hand (see calibration). Keys in the program's window: m both arms to the middle of their range, w sweep the ranges, p the leader keeps carrying the cube into the bowl, 1–6 and the arrow keys move one leader joint, s stop, c cube back, q quit. From a script use node tools/sil/so101-virtual.mjs ctl <command> (see --help for the list).

04 — Servo IDs

Servos "out of the box": lerobot-setup-motors

New servos all have ID 1. With --factory the virtual arm behaves the same: at first only the gripper servo is connected to the board. As soon as LeRobot has written its ID and you press Enter for the next motor, the program "moves the cable" to the next servo, in exactly the order LeRobot asks for. At the end it connects the whole chain.

# terminal 1 (a separate arm just for this step)
node tools/sil/so101-virtual.mjs --factory --follower-port /tmp/so101-factory --ctl-port 8766

# terminal 2: press Enter six times
lerobot-setup-motors --robot.type=so101_follower --robot.port=/tmp/so101-factory

LeRobot prints "'gripper' motor id set to 6" down to "'shoulder_pan' motor id set to 1". The same with a guided walkthrough: Servo setup dry run.

05 — Calibration

Press Enter twice per arm

lerobot-calibrate --robot.type=so101_follower --robot.port=/tmp/so101-follower --robot.id=sil_follower
lerobot-calibrate --teleop.type=so101_leader --teleop.port=/tmp/so101-leader --teleop.id=sil_leader

Calibration has two steps. "Move … to the middle of its range of motion and press ENTER": with --auto-hand the arm is already in the middle of its range, just press Enter. LeRobot writes the zero offset (Homing_Offset). The program notices and moves every joint (except the wrist roll, which LeRobot treats as a full turn) from one end stop to the other, which takes about half a minute. When the program's window says "sweep done", press the second Enter in LeRobot. Without --auto-hand use the m and w keys.

Mind the IDs. LeRobot stores the calibration under --robot.id and --teleop.id. Use different IDs for the virtual arms than for the real ones (here sil_follower and sil_leader), otherwise the virtual calibration overwrites the real one.

06 — Teleoperation

The leader leads, the follower follows

Press p in the program's window: the virtual leader starts carrying the cube into the bowl, over and over. Then:

lerobot-teleoperate \
    --robot.type=so101_follower --robot.port=/tmp/so101-follower --robot.id=sil_follower \
    --teleop.type=so101_leader --teleop.port=/tmp/so101-leader --teleop.id=sil_leader

The loop runs at 60 Hz; the follower copies the leader in the physics simulation and really lifts and carries the cube. Stop with Ctrl+C. To play your own leader motion, pass a file: --leader-motion trajectory.json (a list of {"q": [6 angles in radians], "t": seconds}) or a CSV with rows t,q0,…,q5.

07 — Dataset

Recording demonstrations: lerobot-record

export HF_HUB_OFFLINE=1
lerobot-record \
    --robot.type=so101_follower --robot.port=/tmp/so101-follower --robot.id=sil_follower \
    --teleop.type=so101_leader --teleop.port=/tmp/so101-leader --teleop.id=sil_leader \
    --dataset.repo_id=local/so101_sil --dataset.root=$HOME/so101_sil_dataset \
    --dataset.single_task="Put the cube in the bowl" \
    --dataset.num_episodes=2 --dataset.episode_time_s=12 --dataset.reset_time_s=4 \
    --dataset.push_to_hub=false --play_sounds=false

This creates a LeRobot-format dataset (parquet with joint positions and actions, 30 frames per second) in ~/so101_sil_dataset. Nothing is uploaded to Hugging Face and no token is needed. Without the --camera switch the dataset holds joint positions only; the virtual cameras are covered in the next section.

08 — Replay

The policy path: lerobot-replay

Stop the leader with s and replay a recorded episode on the follower. It is the same path a trained policy's actions take later (send_action → Sync Write Goal_Position):

lerobot-replay \
    --robot.type=so101_follower --robot.port=/tmp/so101-follower --robot.id=sil_follower \
    --dataset.repo_id=local/so101_sil --dataset.root=$HOME/so101_sil_dataset --dataset.episode=0 \
    --play_sounds=false

To run a trained policy with cameras (lerobot-rollout), see the next section.

09 — Policy

First task with a pretrained policy

A policy is a neural network that turns camera images and joint positions into where the arm should go next. The Hugging Face Hub has public policies trained on the SO-101. Since 7 Nov 2026 the virtual arm also has virtual cameras, so you can run such a policy against it before you build the arm. It is a test of the whole camera → policy → servos path, not a success-rate contest: the policy learned on a different table, with different cameras and from real photos.

Tested on 7 Nov 2026 with LeRobot 0.6.1 and pyzmq 27, CPU only: three runs of the real policy on GitHub Actions (ubuntu-latest, 4 cores, Python 3.12, PyTorch 2.11, Node.js 24) and runs with a network of the same size on our two-core machine (Python 3.13, PyTorch 2.7, Node.js 22). The script and the workflow are in the repository: tools/sil/policy_trial.py, workflow sil-policy-trial.

Which policy

We use samarth-shukla6/act-svla-so101-pickplace: an ACT policy under the Apache-2.0 licence, 51.7 million parameters (a 206 MB file). It was trained on the public dataset lerobot/svla_so101_pickplace (Apache-2.0, 50 episodes, 11,939 frames, 30 frames per second; its meta/info.json lists robot_type so100_follower even though it is named after the SO-101) with two cameras, up and side, at 640 × 480. We picked it because it is small, permissively licensed, has known camera names and resolution, and runs on a CPU. Its model card is only the generic LeRobot template, though: it gives no success rate and does not say where the cameras were.

We also looked at pepijn223/odsc-so101-act (Apache-2.0, trained directly in MuJoCo). It belongs to its own five-object scene, wants top and wrist cameras at 384 × 384 and joint angles in radians, so it does not run with lerobot-rollout and the SO-101 follower without conversion. SmolVLA policies have about 450 million parameters and are much slower on a CPU.

1. The virtual arm with cameras

pip install "pyzmq>=26.2.1,<28"        # LeRobot's ZMQ camera needs it
node tools/sil/so101-virtual.mjs --auto-hand --camera up --camera side

The program prints cameras: up (up), side (side) 640x480 @ 15 fps -> zmq tcp://127.0.0.1:5555. It draws the scene with its own simple renderer (flat colours, no textures or shadows) and sends the frames over ZeroMQ in the format of LeRobot's built-in type: zmq camera. So LeRobot stays unmodified and nothing is added to its code. To see what the policy sees, open http://127.0.0.1:8765/camera/up.png and …/camera/side.png in a browser. Other views: front and wrist (the wrist camera from the arm model); give a different name for LeRobot with --camera top=up.

2. Calibrate and run

Calibrate the follower as in Calibration (once is enough). Then, in a second terminal:

lerobot-rollout --strategy.type=base \
    --policy.path=samarth-shukla6/act-svla-so101-pickplace \
    --policy.pretrained_revision=c903979a9d73104d38f6daac5266962128a99219 --policy.device=cpu \
    --robot.type=so101_follower --robot.port=/tmp/so101-follower --robot.id=sil_follower \
    --robot.use_degrees=false \
    --robot.cameras="{ up: {type: zmq, server_address: 127.0.0.1, port: 5555, camera_name: up, width: 640, height: 480, fps: 30}, side: {type: zmq, server_address: 127.0.0.1, port: 5555, camera_name: side, width: 640, height: 480, fps: 30} }" \
    --task="Pick up the cube and place it in the bowl" --duration=20 --play_sounds=false

--policy.pretrained_revision pins exactly the model version we tested; without it LeRobot downloads the latest. Why --robot.use_degrees=false. This policy's dataset was recorded in units of −100 to 100 (as older LeRobot versions wrote them), while LeRobot 0.6.1 sends degrees for the SO-101 by default. With the wrong units the policy gets meaningless joint positions. The camera names (up, side) must match what the policy expects; you find them in the model's config.json.

What you will see. On the first run LeRobot downloads the model (about 210 MB, no token) and torchvision's ResNet18 weights (about 45 MB). Then ZMQCamera(up@127.0.0.1:5555) connected, the arm switches its motors on and starts to move. Messages like “Record loop is running slower (… Hz) than the target FPS (30.0 Hz)” are normal on a CPU. After 20 seconds you get “Duration limit reached (20s)”, the arm returns to where it started and “Rollout finished”.

CPU time. ACT computes 100 steps at once (3.3 s of motion) and the arm stands still while it computes. On our machine with two shared cores one computation took 0.8 to 5 s. On GitHub Actions with four cores LeRobot reported a slow loop only five or six times per run, and a whole run with --duration=20 took 34 to 37 s (including loading the model and returning the arm).

One command does all of it, with a record of the joint motion and camera snapshots (it starts the virtual arm, calibrates it and runs the policy): python3 tools/sil/policy_trial.py --out /tmp/trial. The result is in /tmp/trial/summary.md.

What to expect, and the limits

In all three runs the arm moved the whole time and the gripper opened and closed. In the two runs where we measured it, the gripper went from 26 to 29 cm away from the cube to 4.9 to 5.6 cm from it within 3 to 4 s, and came down to 0.5 cm above the table. It did not pick up the cube or move it, though (0.0 cm). The motion is jerky because the arm stands still during each computation. Why the task does not work out:

  • The policy learned from real photos of a different table. Our virtual cameras stand elsewhere and the image is drawn, so the policy sees something it has never seen.
  • The calibration differs: for example, wrist roll spans −92 to −20 in the dataset and comes out differently on our virtual arm. The same number does not mean the same pose.
  • The physics is an approximation (servo friction, elasticity and backlash are missing), and the cube and bowl are not where they were in the dataset.
  • Success or failure in the virtual scene says nothing about how the policy will do on a real arm. A reliable policy for your own table comes from your own demonstrations (lerobot-record and lerobot-train).

Later, on the real arm

The same command works with the real arm: change the port and the cameras (type: opencv). Only do it once the arm works reliably in teleoperation. A policy can send the arm anywhere within the range you set during calibration, and quickly. Clear the workspace, keep fingers away from the gripper, keep a hand on the power switch and start with --robot.max_relative_target=5 (LeRobot then moves each step's target at most 5 joint units away from the current position). Children only with an adult present. Our browser guide does not drive a real arm at all without the ?real=1 parameter; running a policy on a real arm is at your own risk.

10 — Live view

See the virtual arm in your browser

With --mirror the program streams the joint angles and the cube pose over a WebSocket, on this computer only (127.0.0.1). Serve the downloaded copy of the website and open the simulation with ?mirror=8765:

python3 -m http.server 8123 --bind 127.0.0.1
# in the browser: http://127.0.0.1:8123/sim/so101/?mirror=8765

"LeRobot mirror: live" appears bottom left and the arm in the browser moves the way LeRobot drives it. The page's own physics is off meanwhile; only the program computes.

11 — Emulation

What is real and what is emulated

Real, unchangedEmulated or approximate
LeRobot 0.6.1 and its commands, the Feetech SDK, pyserial, the packet format, register addresses, sign encoding, 1 MbaudThe STS3215 servos: register table from LeRobot, behaviour from its code. Factory values (firmware 3.10, voltage limits, PID, current protection) are plausible, not from a datasheet
The dataset format, calibration files, the teleoperation loopLoad, current and heat are a rough model. Gear backlash, compliance and servo friction are missing; contacts in the physics are an approximation
Safety of the browser wizardThe virtual servos report firmware "emulated". The wizard never counts it as verified firmware of real servos

Other differences: the leader is kinematic (its 1:191 and 1:147 gear ratios have no effect), replies come without delay and without an echo of the sent packet (like the Waveshare board), and only 1 Mbaud is tested. A calibration made on the virtual arm does not apply to the real arm; calibrate the real arm again.

12 — Windows

Windows: use WSL, or com0com (untested)

Windows has no pseudo-terminals. The simplest way is to run the program and LeRobot inside WSL (Ubuntu), where everything works as on Linux. Natively you could use a pair of virtual COM ports from the com0com driver and adapt the program to read one of them; we have not tried that.

13 — Troubleshooting
  • "There is no status packet!" No reply within 50 ms. It can happen now and then on a very busy computer (like a loose cable on a real arm). Run the command again, or close heavy programs.
  • "Some motors have the same min and max values". You pressed Enter before the sweep finished. Wait for "sweep done".
  • The port does not open. Is the program running? The path in --robot.port must match the one it printed.
  • After calibration the follower moves differently from the leader. Calibrate both arms with --auto-hand (or the w key) so they have the same ranges.
