# backend/forge: agentic CAD forge (stage 0 demo)

A request such as *„SO-101 s baterkou (flashlight)“* goes in. The forge picks a mount point on the robot,
writes build123d CAD, checks the part (print, mass/torque, collisions in MuJoCo, power), picks real parts
with dated sources, renders it in the assembly-guide style and drafts a guide section. Every step goes
into a job log that the `/lab/` page replays. Later the same log is streamed live over SSE.

**Stage 0 = no LLM.** The "brain" (`ScriptedBrain` in `forge/pipeline.py`) is deterministic rules
plus a CAD source written by Claude (`designs/so101_flashlight.py`). That source goes through **the same
`run_cad` sandbox an LLM will use**. An `LLMBrain` (OpenRouter) will implement the same methods
(`parse`, `choose_mount`, `params`, `write_cad`, `pick_led`). The API key is added by the owner as a
server secret. Nothing in this directory reads, stores or needs a key.

Why `backend/forge/` and not `tools/`: it is a service that will run on the VPS as an isolated worker
(like `backend/api`, `backend/bridge`). The site only gets its published outputs (draft pages, images,
lab replay, BOM delta). The render step reuses `tools/render-kit/so101-steps.html` through
`tools/render-kit/forge-render.mjs`.

## Layout

| Path | What |
| --- | --- |
| `forge/policy.py` | Static AST allowlist for CAD source (stdlib only) |
| `forge/sandbox.py` | `run_cad(source, job_dir)`: policy → isolated child process → STEP + STL + geometry report |
| `forge/_child.py` | Code that runs inside the sandbox process (policy re-check, audit hook, restricted builtins, export) |
| `forge/geometry.py` | Report: bbox, volume, mass (PLA 1.24 g/cm³, solid and FDM estimate), centre of mass, watertight, min wall (ray-based) |
| `forge/mounts/so101.json` | SO-101 mount-point library (generated by `tools/measure_so101.py` from `sim/so101/model`) |
| `forge/sim.py` | MuJoCo: copy of the model with the part attached, collision sweep, static fit, gravity torque |
| `forge/checks.py` | Printability, LED circuit (resistor, current range, power) |
| `forge/parts/catalog.json` | Curated parts with sources (URL, checked date, status), data/components structure |
| `forge/pipeline.py` | The job: parse → mount → cad → checks → parts → render → guide; `--publish` copies outputs into the site |
| `designs/so101_flashlight.py` | The demo's CAD source (Claude-authored, parametric: LED Ø, tilt, toe, wall, …) |
| `templates/guide.{cs,en}.html` | Guide section templates, filled from the job's numbers |
| `examples/so101-flashlight/` | Published job outputs: `design.py`, `part.step`, `part.stl`, `led.stl`, `report.json`, `checks.json`, `electrical.json` |
| `tests/` | `test_sandbox.py` (policy + malicious inputs), `test_pipeline.py` (deterministic re-run vs. published outputs) |

Published into the site by `--publish`: `img/forge/so101-flashlight/*` (renders),
`tools/content/forge-flashlight.{cs,en}.html` (guide draft; `draft: true` in `tools/build.mjs` → noindex,
not in the sitemap, not linked), `lab/forge/so101-flashlight/job.json` (replay for `/lab/`),
`data/components/extensions/so101-flashlight.json` (BOM delta, same component/source fields as
`data/components/so101.json`; in a subfolder so the purchase-plan build check does not treat it as a
robot plan; `tests/test_pipeline.py` validates its sources instead).

## Running

```sh
pip install -r backend/forge/requirements.txt          # build123d, trimesh, mujoco, numpy, rtree
cd backend/forge
python3 -m unittest tests.test_sandbox -v               # ≈ 40 s
python3 -m unittest tests.test_pipeline -v              # ≈ 2.5 min (full job without renders)
python3 -m forge.pipeline "SO-101 s baterkou" --job /tmp/forge-job            # + renders (needs node + Playwright)
python3 -m forge.pipeline "SO-101 s baterkou" --job /tmp/forge-job --publish  # write the site outputs
python3 tools/measure_so101.py [--check]                 # regenerate / verify the mount library (run from the repo root)
```

## `run_cad`: the sandboxed CAD tool

Input: build123d Python source that assigns the final solid to `result` and may set a JSON-able `meta`
dict. Output: `{ok, stage, errors, report, files, stdout, elapsed_s}`. `stage` is one of
`policy | exec | export | timeout | killed | isolation | report | done`.

Layers (each one alone stops the malicious inputs in `tests/test_sandbox.py`):

1. **Static policy** (`policy.py`): imports only `build123d`, `math`. No names or attributes starting
   with `_`, no string constants containing `__`. No `eval/exec/compile/open/__import__/getattr/
   setattr/globals/vars/type/…`, no `.format`, no attributes naming modules or process/file calls
   (`os`, `sys`, `subprocess`, `system`, `popen`, `run`, …), no `export_*` / `import_*` / `read*` /
   `write*` names (build123d writes files through native code that an audit hook cannot see). No classes,
   `global`, `yield`, `async`, decorators, bytes literals, shifts, huge int/exponent/sequence literals.
   Source ≤ 64 KB, ≤ 20 000 AST nodes, nesting ≤ 60. Rejected source never runs.
2. **Separate process** `python -I forge/_child.py <work>`: new session, empty environment, cwd = a fresh
   private temp dir (the only place it can write; results are copied back). Limits: address space
   (default 2 GB), CPU seconds, file size 64 MB, 64 open files, no core dumps.
3. **No network**: `os.unshare(CLONE_NEWNET)` (as non-root with `CLONE_NEWUSER`). If the namespace
   cannot be created `run_cad` refuses to run (fail closed).
4. **Unprivileged**: when the worker runs as root, the child drops to uid/gid 65534 (nobody).
5. **Inside the child**: policy checked again; `build123d` imported before an audit hook goes in. The
   hook then refuses sockets, subprocess/exec/fork/spawn, ctypes, `compile`/`exec` after the one
   allowed exec, writes outside the work dir and reads outside the Python installation. The code runs with
   a minimal builtins table and an `__import__` that only returns `build123d`/`math`.
6. **Wall-clock timeout** (default 90 s): the whole process group is SIGKILLed.

Tested (`tests/test_sandbox.py`): 41 policy cases (`import os`, `open()`, `__import__`, `getattr`
string tricks, dunder chains, format-string escapes, generator frames, `build123d.<module>.os`,
`export_step` to an arbitrary path, `import_step('/etc/passwd')`, power/sequence blow-ups, …), plus run-time cases:
infinite loop (killed by timeout), memory bombs (MemoryError / killed), recursion bomb, missing `result`,
and a probe that the same pre-exec gives no network, uid nobody and the address-space limit.

## SO-101 mount library (`forge/mounts/so101.json`)

Measured by `tools/measure_so101.py` on the sim meshes (`sim/so101/model`, MuJoCo Menagerie
robotstudio_so101, Apache-2.0). Mesh vertices are placed into the MuJoCo **body** frame. Flat faces come from
face normals, holes from closed, near-circular loops in plane sections. The meshes are **decimated**: small
features move by a few tenths of a millimetre and holes read small. Every interface therefore carries an
uncertainty and `"verify": "ověřit na tisku"`.

| id | body | kind | what was measured |
| --- | --- | --- | --- |
| `gripper_cam_face` | gripper | 2 screw holes | +y face of the fixed jaw at y = 24.0 mm (407 mm² flat). Holes Ø3.2 at x −5.0 / 3.1, z −23.4 (pitch 8.1 on the jaw mesh, 7.6 on the camera-mount mesh → design 8.0 ± 0.6, slotted). Ø5.1 pocket 4 mm below the face. Used by the official wrist-camera mount. |
| `gripper_outer_face` | gripper | flat, no holes | −x face at x = −35.2 mm, 847 mm², Ø10 recess coaxial with the jaw servo: tape or clip only |
| `forearm_clamp` | lower_arm | band clamp | constant section 24.0 × 52.0 mm for x −90…−50 mm: for add-ons that should not roll with the wrist |

## The demo result (flashlight)

* Part: plate on the camera face (sandwiched under the camera mount, which moves +3 mm) + a sleeve for a
  10 mm LED, tilted 25° so the axis passes the gripper TCP site. Toe 0° keeps the sleeve inside the jaw outline.
  ≈ 2.4 g PLA, thinnest wall 1.22 mm (LED collar seat), watertight, single solid.
* Checks: added mass ≈ 5.4 g (part + LED + resistor + 2 g of cable). Static wrist-flex torque +3.5 % (0.135 N·m,
  8 % of a 7.4 V STS3215). Collision sweep over 9 900 poses, 8 644 where the robot itself is clear:
  contact only in 2 fully folded arm configurations (×4 gripper states). In those the robot's own jaw is already within
  2.5 mm of the base. Static fit: no interference with the jaw or the camera mount.
* Power: USB 5 V (PC port or charger) + 120 Ω → 14 mA typ., ≤ 19 mA worst case. Alternative: buck module
  to 5 V from the servo PSU. No mains, no LiPo.

## VPS deployment design (design only, nothing is deployed by this PR)

```
browser ── POST /forge/jobs (invite token) ──► backend/api ──► queue (SQLite table, 1 row per job)
   ▲                                              │
   └── GET /forge/jobs/<id>/events (SSE) ◄────────┘◄── job events (append-only) ◄── forge-worker (container)
                                                                                     │
                                                       OpenRouter (LLM) ◄────────────┤ only egress
                                                       GitHub (draft PR via API) ◄───┘ (separate step)
```

**Worker container (`forge-worker`)**, its own image (`python:3.12-slim` + build123d/OCP, trimesh,
mujoco; node + Playwright Chromium for renders in a second, render-only container if the image gets
too big):

* runs as a non-root user, `read_only: true` root filesystem, `tmpfs` for `/tmp` and the job dir only
  (size-capped), `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, seccomp default profile.
  Ideally under **gVisor** (`runtime: runsc`) so a kernel bug in OCP/MuJoCo native code is contained
  too. Alternative: run `run_cad` children under **nsjail** with its own mount/pid/net namespaces.
* `run_cad` keeps its in-process layers. `os.unshare` needs user namespaces inside the container (gVisor
  and nsjail provide them). Otherwise the worker sets `FORGE_NETNS=external` and relies on the
  container having **no network** for the CAD step: the CAD sandbox runs in a sidecar container with
  `network_mode: none`, and the worker talks to it over a unix socket on a shared tmpfs.
* limits: `cpus: 1.0`, `mem_limit: 2g`, `pids_limit: 128`; per job a wall-clock cap (CAD 90 s per
  call, whole job 15 min) and a cap on run_cad calls per job (e.g. 12).
* **no Docker socket**, no host network, no host volumes except the read-only model data baked into
  the image; never binds 80/443 (Caddy stays the only public listener; the worker listens nowhere and
  pulls jobs).
* egress: the LLM container step may reach only `openrouter.ai` (egress proxy allowlist); the CAD
  sandbox has no network at all. The OpenRouter key is a server-side secret (env from the deploy
  secret store, never in the repo, never visible to CAD code since the child gets an empty env).

**Queue and API (`backend/api`)**: `POST /forge/jobs {request}` with an invite token (header).
Validates length/language and enqueues. Response: `{id}`. `GET /forge/jobs/<id>` returns the job.json.
`GET /forge/jobs/<id>/events` is **SSE**. Each event is one step change (`{step, status, summary,
data, artifacts}`), exactly what `/lab/` already replays (`applyEvent`). Caddy: `flush_interval -1` for
the events route (same as the MCP SSE route). Artifacts (STL/STEP/renders) are served from the job store
with `Content-Disposition: attachment`, never executed.

**Budget caps**: per job a max LLM spend (e.g. $0.50, tokens counted from OpenRouter usage fields) and
max run_cad calls. Per invite token a daily job count (e.g. 5/day). Globally a daily spend cap
(e.g. $10/day) checked before every LLM call. When a cap is hit the job ends with `status: "budget"` and
the SSE stream says so. Spend is logged per job (no request bodies in logs).

**Invite tokens**: random 128-bit tokens stored hashed in the api's SQLite, each with a label, a daily
quota and an expiry. Revocable. Rate limit per token and per IP (existing `ratelimit.ts`).

**Review via draft PR**: a finished job never goes live by itself. A separate, manually triggered
step (or a maintainer clicking "propose") publishes it with `pipeline.publish()` into a branch and opens a
**draft PR** through the GitHub API using a fine-grained token limited to this repo (contents + pull
requests). The pages stay `draft: true` (noindex, unlinked, labelled "komunitní návrh – ověřeno pouze v
simulaci") until a human has printed and fitted the part and removes the flag in review.
